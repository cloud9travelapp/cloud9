# Project handoff — Cloud9

AI travel-planning web app. Next.js 16 (App Router, Turbopack) · React 19 · TypeScript · Tailwind v4 · NextAuth v5 (Google → Supabase) · Anthropic SDK (claude-opus-5 concierge, claude-haiku-4-5 namer). Repo `cloud9travelapp/cloud9`, deploys to Vercel from `main`. Mock providers need no env vars.

## Architecture (key patterns)
- **Chat**: streaming route `app/api/chat/route.ts`. The system prompt IS the concierge's behavior spec. Tool round-trip loop supports multiple tools; auth-gated; saves to Supabase. Model history window = the LATEST 40 messages (desc + reverse — taking the oldest was the "context bleed" bug; same for the 200-message display window in `app/chat/page.tsx`). **Narration leak = a MODEL-CONFIG problem, not a prompt problem** (learned the hard way 2026-07-26): with `thinking:{type:"disabled"}`, Opus 5 writes tool-decision reasoning straight into the visible stream (full English deliberation mid-Hebrew turn). TWO dynamic-tail prompt rules failed live — the second was parroted back verbatim as the reply's first words. The fix is `thinking:{type:"adaptive"}`: reasoning goes into thinking blocks, and the stream loop forwards `text_delta` ONLY, so it can never reach the user. Do not "solve" a future narration leak with prompt wording. (`remember_preference` calls carry no text at all.)
- **Runtime diagnosis = SQL, not logs**: `lib/diag.ts` `logDiag(kind, detail)` → Supabase `diag_events` (best-effort, console-mirrored). Instrumented: every tool_call (+outcome), search errors (real cause), stays quota fallback, stream errors, title errors, `chat_usage` (per-turn tokens — input/cache_read/cache_write/output — plus `gap_s`, the pause since the previous message, and `hops`/`history_len`: the cost-and-cache evidence base). Vercel's ~1h log retention makes log-hunting a dead end — query `diag_events` instead. Extend this pattern for any new "what happened at runtime?" question.
- **Trip titles**: `deriveTripTitle` (haiku) runs each turn via `after()` (never blocks the stream) — returns a title covering ALL destinations ("Japan & Korea") or KEEP (defined strictly: nothing new named, nothing changed — the old "no destination known yet" phrasing made haiku KEEP first turns). While a trip is "New Trip" the titler sees the last ~5 user messages (self-healing). A user rename (pencil in the sidebar → `PATCH /api/trips/[id]`) sets `name_is_custom`, which locks the title against auto-updates. Both paths degrade gracefully if the `name_is_custom` column is missing. Titles use the SHORTEST natural name (never "City, Country"; origin city is never a destination) and pass through the deterministic `sanitizeTripTitle` guard (`lib/trip-title.ts`, unit-tested) before storage.
- **Prompt caching — TWO breakpoints, both `ttl:"1h"`** (round shipped 2026-07-26): (1) STATIC prefix — `systemStatic` (persona + prefs + date + ALL behavior rules; byte-identical across a user's turns), whose marker also covers the 6 tool definitions since render order is tools→system→messages; (2) MOVING history marker — `withHistoryCacheBreakpoint` (`lib/chat/cache.ts`, unit-tested) marks the LAST content block of the LAST message on a COPY per model call, so `anthropicMessages` itself stays marker-free across tool hops. Result: uncached input per turn dropped from ~500-and-growing to 2–6 tokens. `systemDynamic` (per-turn language directive, first/returning line, no-narration rule) sits AFTER both markers — NEVER interpolate per-turn text into the static block, it kills the cache. **Why 1h not 5m** (Max's call, predictability over optimum): writes cost 2× vs 1.25× but reads stay 0.1×, and real users pause 15+ min — nearly half of measured turns blew the 5-minute TTL, each expiry re-billing the whole ~20K prefix. Worst case 5m (~$2.40/conversation) is WORSE than no caching at all; 1h is ~$1.02 regardless of pauses. Each turn logs `chat timing: …| usage: in/cacheRead/cacheWrite/out/hops/gap` AND a `chat_usage` diag row.
- **Timeline ("המסע")** — `trip_timeline_items` (migration 0004, RUN + verified 2026-07-26), generic by `item_type` exactly like `trip_favorites` so future sources need no migration. Tabs שיחה | מסע are CLIENT state in `chat-client.tsx`, never navigation: both panes stay mounted and the inactive one is hidden, so a tab switch keeps chat scroll, any in-flight stream, and (stage C) the map's single initialization. Pure logic in `lib/timeline/present.ts` (day bucketing, overlaps, day numbers, stay spans, progress) is unit-tested; `insertTimelineItem` in `repo.ts` is the ONE write path for all three entry points (REST, chat piggyback, concierge tool), idempotent on `client_ref` — a 23505 means the action already landed, which is SUCCESS.
  - **Selection capture rides in the SAME chat request** as the message it produced (`timelineItem` in the POST body → `X-Timeline-Write: ok|failed` header). Two parallel writes could disagree — the concierge confirming a hotel the timeline never got — and that divergence reads as a broken product. One request either fully lands or fully fails; a retry replays both and can't duplicate (client_ref).
  - **NEVER INVENT A TIME** (the standing rule, phrased to prevent the opposite error too): a real provider-supplied time is a FACT and must be shown even on a `planned` item — a flight's 06:25 comes from the segment data. What's forbidden is inventing one: a planned stay shows no check-in time because we don't have it, and a "15:00" would be fiction. Booked items may carry confirmation times when the wallet lands. So: never invent ≠ never show before booking.
  - **A stay is CONTEXT, not an event**: a subtle band behind the nights it covers (tints ALTERNATE per stay so adjacent stays don't read as one block) plus a recessed per-day strip naming the hotel and night number. Both deliberately lighter than event rows — background, not foreground. **THE NIGHT RULE: you sleep where you check IN**, so the check-out day is a departure and not a night; that one rule makes the transition day (out of A, into B) resolve with no special case.
  - **NO global "draft" mode — decided AGAINST 2026-07-26, do not relitigate.** Reasoning: most of a user's time with us is spent BEFORE anything is booked, so a timeline announcing "none of this is real" undermines the exact phase it exists to serve; and it breaks down logically (hotel booked, flight not — is the timeline draft or booked?). State stays PER ITEM. The "not closed yet" signal is a compact `3 מתוך 5 רכיבים מוזמנים` summary derived from item states.
  - **Known limitation — a MANUAL stay can't span nights.** Check-out lives in the agent snapshot (`item.checkOut`), and manual items have no snapshot, so a hand-added hotel renders as a single day. Not a bug. This WILL surface the moment the wallet ships (manual entry is the whole point there); the clean fix then is an additive `end_date` column.
  - **Map (`journey-map.tsx`, `NEXT_PUBLIC_MAPBOX_TOKEN`)** — Mapbox bills per map LOAD (one unit per `new mapboxgl.Map()`, unlimited interaction after), so exactly ONE Map is constructed and kept alive: the רשימה|מפה toggle hides it with CSS, item changes update markers + the route source in place, and a hidden container gets an explicit `resize()` (it measures zero and renders blank otherwise). The mapbox chunk is `next/dynamic`-loaded on FIRST map open — never in the chat bundle. Lighting follows the app phase via the Standard style's `lightPreset`, wrapped in try/catch so a style change can't break the map. Items without coordinates list under "ללא מיקום" — never dropped, never guessed. Verified live 2026-07-26: token inlines into the client chunk, canvas renders, pins + route draw, phase lighting applies.
    - **`NEXT_PUBLIC_*` is inlined at BUILD time and only where code REFERENCES it** — so "is the token reaching the client?" cannot be answered before the first commit that uses it (an absent token and an unused one look identical). **The token is NOT secret and must never be treated as one**: it's marked "Sensitive" in Vercel, which is contradictory for a NEXT_PUBLIC_ var — the value ships inside the public JS bundle by design and anyone can read it in devtools. The ONLY protection is the URL restriction on the token (cloud9app.io, www, localhost:3000). Never relax that restriction on the assumption that the value is hidden.
    - **Map labels stay LATIN — a DELIBERATE product decision (Max, 2026-07-26), not an oversight. Do not "fix" this.** The map exists for navigating on the ground, and the street sign in Lisbon says "Praça do Comércio", not "כיכר המסחר"; Latin labels match what the traveler is physically reading and avoid transliteration ambiguity. Mapbox Standard renders transliterated Latin even over Israel (verified in Tel Aviv: "Rabin Square", "Habima"), so the vendored RTL plugin (`public/mapbox-gl-rtl-text.js`) currently NEVER FIRES. It stays, registered `lazy` — 133KB that costs users nothing until Hebrew glyphs actually appear, and it becomes MANDATORY the moment anyone calls `map.setLanguage("he")` (without it Hebrew labels render mangled).
  - **Attractions deliberately carry NO date** — the search takes a from/to WINDOW, not a per-activity day, so an activity lands unscheduled until the traveler places it. Assigning it the window's start would be inventing their itinerary. Don't "fix" this.
- **Reply language is computed, never model-inferred**: `lib/language.ts` decides each turn's language (word-dominance of the latest user message; place/brand names don't flip it; ambiguous → conversation's established language; new+ambiguous → Hebrew, the onboarding-preference seam) and the route injects it as a hard per-turn directive covering pre-tool notes, tool summaries, and block strings. Don't add prompt language rules that re-infer from "the user's message" — that was the root cause of the mixed-language bugs.
- **Provider-agnostic search** (real provider = one-file swap): `lib/flights/*` (`search_flights`) and `lib/stays/*` (`search_stays`). Each = types + a `searchX` switch on `X_PROVIDER` env (default `"mock"`, exports `IS_MOCK_*`) + a seeded mock. Don't change existing provider signatures.
- **Known demo limitation — TEST-environment inventory tops out at ~4★** (confirmed 2026-07-21: the cached Paris fetch's star histogram had no 5★; our tercile/star filtering was clean). The luxury band can't show what Hotelbeds test inventory doesn't carry; the prompt's inventory-honesty rule attributes the gap to "my current inventory", never to the city. Re-check when production keys arrive.
- **Hotelbeds provider (LIVE since 2026-07-20)**: `lib/stays/hotelbeds.ts` — APItude geolocation availability search (the concierge passes lat/lng in the tool call, like IATA codes); active via `STAY_PROVIDER=hotelbeds` + `HOTELBEDS_API_KEY/SECRET` in Vercel (base URL defaults to the test host). Evaluation tier = 50 req/day: results cached in Supabase `stay_search_cache` (24h TTL), 45-call/day guard falls back to mock whose `mock-` ids re-label cards as test data. v1 is availability-only for amenities/photos; distance-from-center is COMPUTED (haversine vs the searched point, on cards + in offers JSON for the model). Result pipeline (all unit-tested): PRICE-first budget terciles (≥4★ guard on luxury — real categories don't track price, "€42 4★") → median-relative DISTANCE tier (near half of the set, nearest-first backfill to 5; `distanceFilter:"any"` tool param skips; user-named area moves the searched point itself) → 8-card cap → worth-it DEAL detection (far offer ≥30% under shown same-star median, split into the tool JSON as `deal`, offered via one sanctioned teaser sentence — the only question allowed in a cards message).
- **Hotelbeds ACTIVITIES provider (LIVE since 2026-07-23)**: `lib/attractions/*` mirrors the stays abstraction (`ATTRACTION_PROVIDER=hotelbeds` + `HOTELBEDS_ACTIVITIES_API_KEY/SECRET` in Vercel — a SEPARATE key with its OWN 50/day eval quota; same SHA-256 signer via `activitiesHeaders()` in `hotelbeds-auth.ts`). Hard-won API facts (each was a live-debugging round — trust these over the docs' ambiguity): **availability** = `POST /activity-api/3.0/activities/availability` (the `/availability` suffix is required; the GPS filter is EXACTLY `{type:"gps", latitude, longitude}` — NO radius/unit, unlike Hotels; `paxes:[{age}]` is MANDATORY or you get 200-with-empty; gps can't combine with a destination filter). **Content** = the MULTI form `POST /activity-content-api/3.0/activities/` `{language, codes:[{activityCode}]}` → `activitiesContent[]` (the simple GET needs a modality code we don't track). **Media shape**: `media.images[]` each `{visualizationOrder, urls[]}` where `urls[]` = size VARIANTS of the same photo `{sizeType, resource: absolute URL}`; `extractActivityImages` picks ONE variant per image by preference (XLARGE-first for the modal gallery, LARGE2-first thumbs for cards), sorted by visualizationOrder — never dump variants or one photo becomes six slides. **Batch prefetch**: one content call per live search caches the whole stack permanently (`attraction_content_cache`, versioned `v` — bump to invalidate re-mapping); quota accounting counts each live search DOUBLE (availability + batch content) + `src:"single"` fallback rows once; in-flight promise maps dedupe same-code races (both hotels + attractions). Empty live results stay HONEST (no mock; mock only on error/guard-trip); `contentUnavailable` drives the "photos couldn't load" note. Every search leaves ONE `attraction_search_trace` diag row (source: cache | live:real | live:empty | mock:guard | mock:error + status/counts/quota headers) — a silent fallback is a bug. **Eval-tier quirks to recheck with production keys**: some activities are 0-priced, descriptions may embed "Highlights:" text, and category inference is keyword-based (a tuk-tuk tour filed under "Food & drink") — tune `toCategory` against real segmentation data then.
- **QUOTA vs RATE LIMIT — two DIFFERENT ceilings; do not conflate them (settled 2026-07-27, do not relitigate).** Live Activities responses carry `x-ratelimit-limit: 5000` / `x-ratelimit-remaining: ~4996`, which looks like our 45/day guard is ~100× too strict. It is NOT. Hotelbeds' own getting-started doc states the evaluation key allowance is **50 requests per day, and exceeding it returns 403** — and it documents NO `x-ratelimit-*` headers at all. So the 5000 header is an UNDOCUMENTED gateway/burst limit on a different window, not the daily quota; the daily quota is invisible in headers and only announces itself as a 403. That 403-on-exceed is exactly the `hotel_content_cache` burn signature (see `memory/content-403-looks-like-broken-gallery`). **Never loosen `DAILY_CALL_BUDGET` on the strength of the 5000 header.** Both providers now log `hotel_quota_headers` / `quotaHeaders` on every live call so the two counters can be watched separately. Evidence the guard was NOT the cause of the empty-London round: those traces read `source:"live:empty"`, never `mock:guard` — the guard never fired.
- **Preferences (ask-don't-assume)**: the concierge records ONLY explicitly-stated/confirmed preferences via the `remember_preference` tool — scope `stable` → `users.preferences` (crosses trips, in the static prompt's profile line), scope `trip` → `trips.preferences` jsonb (dynamic tail; dies with the trip). Known preferences open as questions ("גם הפעם?"), never silent filters. The old keyword auto-learner (`lib/preferences.ts`) is deleted — do not reintroduce inference-based preference learning.
- **Delimiter blocks**: the model appends ONE `<<OPTIONS>> | <<FLIGHTS>> | <<STAYS>> … <<END>>` block per message. Frontend `components/chat/chat-client.tsx` parses via `displayText` (strips from the first `<<`, so raw blocks never leak) + tolerant `blockRaw`. Card views live in `components/chat/message-parts.tsx` (shared by the real chat AND the landing demo, so they can't drift). Shared `CardSelect` action posts a structured choice as the user's message.
- **Standing UI rule — minimum 24px tap targets on EVERY interactive control**, destructive ones especially. A text-sized link is ~18px tall, which is a miss on a thumb; add height with padding (invisible) rather than making the control look heavier. This is a constraint on every new component, not a one-off fix. Verify by MEASURING (`getBoundingClientRect`) at 390px, never by looking.
- **Design system**: time-of-day phase tokens (`--c-*`) under `[data-phase]` in `app/globals.css`; 5 phases (sunrise/morning/midday/sunset/night) set from local time (flash-free via a `next/script` inline init). Suez One (display) + Heebo (body). Chat is RTL-first with per-message `dir="auto"` + `unicode-bidi: plaintext`; times/codes/prices stay LTR. Every animation is gated under `prefers-reduced-motion`.
- **Brand**: `components/brand/` (cloud mark + `Lockup`); favicon `app/icon.svg` + `app/apple-icon.tsx`; social image `app/opengraph-image.tsx` (fixed sunset palette).

## Working process
- **AN OUTLIER IS NOT JUST A BAD ROW — IT POISONS EVERY STATISTIC DERIVED FROM THE SET.** Max's framing, 2026-07-27, and the bigger half of the Sorrento finding. Two corrupt hotels (7,429 and 3,891/night) were reported as "two ugly cards", but the pipeline computes PRICE TERCILES for budget bands and a SAME-STAR MEDIAN for deal detection over the same array — so every "mid-range" search run before the fix had a 7,429/night phantom inside its statistics, mis-banding all 38 legitimate hotels. The lesson generalises: whenever a bad record enters a set that something later aggregates (median, tercile, average, min/max, "cheapest", "typical"), the blast radius is the whole aggregate, not the record. So filter corrupt data BEFORE any statistic is derived from it (`dropPriceOutliers` runs ahead of `filterForBudget` and `detectDeal`), and when you find one bad row, immediately ask what else consumed that array.
- **"IS IT US OR THEM?" — FIND A SECOND INDEPENDENT FIELD THAT SHOULD AGREE, AND COMPARE.** This is the cross-check that makes a provider-blaming conclusion trustworthy instead of a convenient excuse, and it is reusable for every future value-looks-wrong question. Worked 2026-07-27 on the Sorrento 10× price: the card price comes from `hotel.minRate`, the room prices come from `room.rates[].net` — different fields, different code paths, both cached. They agreed EXACTLY (33,426 = 33,426), which exonerated the mapper; had they disagreed, the mapper was the bug. Corroborate further with (a) internal coherence — Michelangelo's ONLY room was an "Economy … no elevator" at the top price, and its BB and RO rates were identical (free breakfast is not a real rate structure), while Capodimonte's 9 rooms rose monotonically basic→suite; and (b) the population — 38 of 40 hotels were plausible, so it is per-record corruption, not a systemic mapping fault. **Never conclude "bad test data" from a single field or a single record** — three times in one week that assumption turned out to be a mapping bug (the attractions group-total-labeled-per-person among them). And note the corollary: even when the provider IS at fault, "they sent it" is not a shippable answer — hence `dropPriceOutliers`.
- **MEASURE, don't eyeball — never trust a screenshot for anything with a numeric threshold** (colors, sizes, spacing, opacity). Two bugs in ONE round (2026-07-26) looked perfect in screenshots: (1) a stay band was **fully transparent** because `bg-c-cloud/50` names a color Tailwind doesn't have — only the nine `--c-*` roles in `@theme` are mapped, and an unmapped name compiles to NOTHING, silently; (2) a destructive "הסרה" control measured **25×18px**. Both were caught by reading `getComputedStyle` / `getBoundingClientRect` through the browser tools. For any visual change, assert on computed values, not on how the picture looks.
- **Confirm the new build is actually being served BEFORE trusting a measurement.** Twice in that round the measurement ran against the previous deployment and returned the old numbers. A stale measurement reads exactly like a failed fix — the same trap that cost two days on the hotel images. Cheap check: fetch the served CSS/JS bundle and grep for a string only the new build contains (e.g. the new class name), or confirm the deployment SHA is Ready, then measure.
- Non-trivial features: short plan → **WAIT for approval** → implement.
- Verify locally: `npm run test:unit` (Tier U — free, ~5s, part of the definition of done on EVERY change) + type-check + `npm run build` + preview DOM/computed-style checks. NOTE: the harness preview can't render animations, WebGL, or screenshots — flag those for the user's live review.
- Tier B (behavior harness, "robot Max" — multi-turn conversations vs the chat route with model-call cost) is an approved DESIGN but shelved: implement only if the user pulls the trigger (details in `memory/robot-max-behavior-suite`).
- Small focused commits; push to `main`. **Stage specific files per commit (`git add <path>` — NEVER `git add -A`/`.`)** so unrelated/leftover files don't get swept in (a `git add -A` once committed a stray untracked skill by accident). Temp preview/verification routes are deleted before their commit.
- **Delivery guard — verify the SHA, don't trust the push message.** A change is delivered only when `origin/main` actually points at the expected commit. After every push run `git rev-parse --short origin/main` (or `git log --oneline -1 origin/main`) and confirm it equals the commit you intended — BEFORE reporting anything as delivered. Two silent delivery failures happened in one session: (1) work committed to a worktree branch that was never merged to main; (2) the main worktree in **detached HEAD**, so `git merge --ff-only` advanced the detached HEAD (not the `main` branch ref) and `git push origin main` reported "Everything up-to-date" while origin stayed on the old commit. Push messages lie in both cases — the SHA is the only proof. Also: keep the main worktree ON the `main` branch (`git -C <main> branch --show-current` must print `main`, not empty); if it's detached, `git branch -f main <sha>` (when main isn't checked out elsewhere) then `git checkout main`.
- **WRITE PATHS MUST BE SYMMETRICALLY OBSERVABLE.** When the same logical write has more than one entry point, EVERY path emits the same diag kind — otherwise a failure is visible or invisible depending on which door the user came through, and the quiet door is the one that rots. Found 2026-07-26: `insertTimelineItem` has two callers, and the chat piggyback logged `timeline_write_failed` while the REST route logged NOTHING and returned only `"Timeline is unavailable (migration pending?)"` — the exact silent-failure signature that let the unrun `hotel_content_cache` migration burn the Content quota for days. Both paths now emit `timeline_write_failed` with a `source: "agent" | "manual"` discriminator plus `stage: "validate" | "insert"`, so one SQL query splits failures by entry point. Apply this to favorites, preferences, and any future multi-entry write.
- EVERY Supabase table handover includes GRANT statements (at minimum `grant all on table X to service_role;`) — missing grants on `stay_search_cache` silently killed the cache with 42501 on every write from creation until 2026-07-20 (every search burned live quota). Grants audit ran 2026-07-20.
- **A handed-over migration is NOT done until Max confirms he RAN it AND the session VERIFIES the table exists** (one probe: PostgREST 406 = table exists/empty row, 404 = table MISSING). The `hotel_content_cache` handover sat unrun for days — and because the cache reads are best-effort, the 404s never stopped the live Content calls: every modal open + card-gallery fetch hit Hotelbeds directly with nothing ever cached, silently burning the full 50/day Content quota daily and presenting as "the gallery broke". Handover ≠ done; track pending migrations as OPEN blockers and verify on the next session's first touch. (Full pattern: `memory/content-403-looks-like-broken-gallery`.)
